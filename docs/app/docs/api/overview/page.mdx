# API Reference: Overview

`stellar-stream-hive-api` is a Rust/Axum service that reads Soroban RPC, decodes
Soroban events emitted by the [Stream contract](/docs/contracts/stream), and
serves the resulting index over a small REST API. It holds everything
in memory (no database). On boot its first poll reaches back
`INDEXER_BACKFILL_LEDGERS` ledgers (default 17,280, about a day), then it
resumes from the last event cursor -- see the
[API repository's README](https://github.com/Stellar-Hive/stellar-stream-hive-api/blob/main/api/README.md)
for why.

Source: [`stellar-stream-hive-api`](https://github.com/Stellar-Hive/stellar-stream-hive-api)
(`api/` directory).

## Base URL

There is no hosted, publicly-maintained instance yet. Run it yourself:

```bash
git clone https://github.com/Stellar-Hive/stellar-stream-hive-api.git
cd stellar-stream-hive-api/api
cargo run
```

By default it binds to `http://localhost:8080`. Every example on these API
reference pages uses `http://localhost:8080` as the base URL -- substitute
your own deployment's host.

## Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | [`/streams`](/docs/api/streams#get-streams) | All known streams, with live-computed accrual |
| `GET` | [`/streams/:id`](/docs/api/streams#get-streamsid) | One stream's full detail |
| `GET` | [`/senders/:address`](/docs/api/streams#get-sendersaddress) | Streams sent by an address |
| `GET` | [`/recipients/:address`](/docs/api/streams#get-recipientsaddress) | Streams received by an address |
| `GET` | [`/stats`](/docs/api/stats) | Aggregate totals across every indexed stream |
| `GET` | `/health` | Liveness check; always returns `200 ok` |
| `GET` | `/ready` | Readiness: `{ synced, latest_ledger, contract_configured, indexed_streams }` |

## Response conventions

- Every response is `application/json`.
- **Amounts are decimal strings, not JSON numbers.** `total_amount`,
  `withdrawn`, `streamed_amount`, `withdrawable_amount`, `total_streamed`, and
  `total_withdrawn` are all serialized as strings (e.g. `"30000000000"`), not
  numbers. This is deliberate: these are `i128` values on-chain, and JSON
  numbers are IEEE-754 doubles in JavaScript/TypeScript, which only represent
  integers exactly up to 2<sup>53</sup> -- well below what a large stream's
  stroop amount can reach. Parse them with `BigInt("30000000000")` in
  JS/TS, or the equivalent big-integer type in your language. See
  [Integration Guide](/docs/integration#computing-streamed_amount-client-side)
  for a worked example.
- Addresses (`sender`, `recipient`, `token`) are Stellar strkeys (`G...` for
  accounts, `C...` for contracts), exactly as they appear on-chain -- no
  reformatting.
- `streamed_amount`, `withdrawable_amount`, and `progress_percent` on every
  stream view are computed **live**, against the indexer's most recently
  observed ledger, on every request -- they are never stale beyond
  the indexer's poll interval (10 seconds by default).

## Error format

Non-2xx responses return:

```json
{
  "error": "not_found",
  "message": "stream '42' not found"
}
```

| HTTP status | `error` | When |
|---|---|---|
| `400` | `bad_request` | A path or limit parameter failed validation (e.g. a malformed address, or `limit` outside `1`-`200`). Its `message` is prefixed with `invalid request: `. Query values the parser cannot read (unknown `status`/`sort`/`order`, non-numeric `limit`/`offset`) return a `400` with a plain-text body instead. |
| `404` | `not_found` | The requested stream id doesn't exist in the index. |
| `502` | `upstream_unavailable` | Reserved for future endpoints that proxy live Horizon reads; unused by the current routes, which only ever read already-indexed in-memory state. |
| `500` | `internal_error` | An unexpected server-side failure (e.g. arithmetic overflow computing aggregate stats). Logged server-side with full detail. The response `message` is prefixed with `internal error: ` and includes the error's description, so do not treat it as opaque. |

### Handling errors in a client

Branch on the `error` field rather than on the HTTP status alone, and treat
`message` as display-ready text for the cases below. Only the kinds in the
table above are ever returned.

```ts
type ApiErrorBody = {
  error: "bad_request" | "not_found" | "internal_error" | "upstream_unavailable";
  message: string;
};

type StreamView = { id: string; /* ...other fields... */ };

async function getStream(id: string): Promise<StreamView | null> {
  const res = await fetch(`http://localhost:8080/streams/${id}`);

  if (res.ok) {
    return (await res.json()) as StreamView;
  }

  const body = (await res.json()) as ApiErrorBody;

  switch (body.error) {
    case "bad_request":
      // The id failed validation (e.g. an empty address). Show the
      // server's message next to the input so the user can correct it.
      throw new ValidationError(body.message);

    case "not_found":
      // No such stream in the index. Render an empty/not-found state
      // instead of an error banner.
      return null;

    case "internal_error":
      // Unexpected server-side failure. Show a generic message and
      // offer a retry; never surface the raw body to the user.
      throw new RetryableError("Something went wrong. Please try again.");

    default:
      // e.g. upstream_unavailable, reserved for future endpoints.
      throw new Error(body.message);
  }
}
```

For a browser example that also reads `X-Total-Count` and pages through list
results cross-origin, see the
[Integration Guide](/docs/integration#browser-example).

### Handling errors in clients

Every non-2xx response uses the same `{ error, message }` shape. A TypeScript
client can branch on the `error` kind to show the user an actionable message:

```ts
interface ApiErrorBody {
  error: string;
  message: string;
}

function userFacingMessage(body: ApiErrorBody, status: number): string {
  switch (body.error) {
    case "not_found":
      return "That stream could not be found.";
    case "bad_request":
      return `Invalid request: ${body.message}`;
    case "upstream_unavailable":
      return "The indexer is temporarily unavailable. Try again later.";
    case "internal_error":
      return "Something went wrong on the server. Please retry.";
    default:
      return `Unexpected error (${status}): ${body.message}`;
  }
}
```

### Why `/streams/:id` can 404 even for a real stream id

<CalloutBox variant="info">
  The indexer only knows about streams whose `create` event it has
  actually observed within its backfill window -- the first
  `INDEXER_BACKFILL_LEDGERS` ledgers (default 17,280, about a day) on
  boot, then every ledger it polls from the last event cursor onward (see
  [why no database](https://github.com/Stellar-Hive/stellar-stream-hive-api/blob/main/api/README.md#why-no-database)).
  If you query a stream id that was created before that backfill window,
  or before `STREAM_CONTRACT_ID` was configured, expect a `404` until the
  relevant event has been re-observed. This is a known v1 limitation, not
  a bug.
</CalloutBox>

## Event wire format

The indexer decodes three Soroban contract events emitted by the
[Stream contract](/docs/contracts/stream#events-emitted): `create`, `withdraw`,
and `cancel` (see `api/src/indexer/events.rs`). Each event's name is its first
topic `Symbol`, followed by the stream id as a second topic (`U64`). The data
is a `Vec` of the remaining fields, in declaration order:

| Event | Topics | Data (`Vec`) |
|---|---|---|
| `create` | `[Symbol("create"), U64(stream_id)]` | `[Address(sender), Address(recipient), Address(token), I128(total_amount), U32(start_ledger), U32(end_ledger), U32(cliff_ledger), Bool(cancellable)]` |
| `withdraw` | `[Symbol("withdraw"), U64(stream_id)]` | `[Address(recipient), I128(amount)]` |
| `cancel` | `[Symbol("cancel"), U64(stream_id)]` | `[Address(sender), I128(streamed_now), I128(remainder)]` |

As returned by Soroban RPC's `getEvents`, each topic and the data value arrive
as base64-encoded XDR `ScVal` strings -- the indexer decodes them with
`ScVal::from_xdr_base64` before matching this shape. These three are the only
events the indexer tracks; the Stream contract's `pause`, `unpause`, and
`admin_transfer` events (and any Vault/Registry events) carry no stream id and
are ignored by the indexer. See
[Events emitted](/docs/contracts/stream#events-emitted) on the Stream contract
page for the consolidated, contract-verified table across all three
contracts.

## What the indexer ignores

Not every event the indexer reads from `getEvents` ends up applied to the
in-memory index (see `api/src/indexer/mod.rs`, `ingest`):

- **Events from rolled-back sub-calls.** Soroban RPC flags each event with
  `inSuccessfulContractCall`. If the sub-call that emitted an event was later
  rolled back (e.g. a failed `require_auth` further up the call tree), this
  flag is `false` and the indexer skips the event entirely -- it never reaches
  the decoder. Rolled-back activity never happened on-chain, so the indexer
  must not materialize it.
- **Malformed or unrecognized events.** If an event's topics or data don't
  match one of the three shapes in
  [Event wire format](#event-wire-format) -- wrong number of fields, an
  unexpected `ScVal` type, or undecodable XDR -- `decode_rpc_event` (in
  `api/src/indexer/events.rs`) returns an error. The indexer logs a warning
  (with the transaction hash and ledger) and moves on to the next event in
  the batch; it never stops the indexer loop or drops the rest of the batch.
  A single bad or unrelated event can therefore never take the service down
  or stall indexing for other streams.

Both behaviors mean the indexer's in-memory state always reflects only events
that actually took effect on-chain. If `/streams/:id` is missing a stream you
expect, check whether its `create` event falls inside the indexer's backfill
window (see
[Why `/streams/:id` can 404 even for a real stream id](#why-streamsid-can-404-even-for-a-real-stream-id))
before assuming it was dropped as malformed.

## Indexer poll cycle

The indexer runs a poll loop on a fixed interval (`POLL_INTERVAL_SECS`,
default 10 seconds). Each tick reads the stored cursor, calls Soroban RPC's
`getEvents`, decodes the returned events, and applies them to the in-memory
store. It then repeats -- reading the cursor again and issuing another
`getEvents` call -- until it reaches the chain tip. A per-tick call cap bounds
how many `getEvents` calls a single tick may make, and the loop stops when the
cursor does not advance (no new events), resuming on the next tick.

## Health and readiness

Two unauthenticated endpoints exist for monitoring and orchestration.

### `GET /health`

```bash
curl http://localhost:8080/health
```

Returns the plain text `ok` with status `200`. It only signals that the HTTP
server is up and answering -- it says nothing about whether the indexer has
synced.

### `GET /ready`

```bash
curl http://localhost:8080/ready
```

```json
{
  "synced": true,
  "latest_ledger": 123456,
  "contract_configured": true,
  "indexed_streams": 42
}
```

`/ready` **always responds `200`**, even when the indexer is not ready, so
clients must read the body rather than relying on the status code:

- `synced` is `false` until the indexer has observed a ledger from Soroban RPC.
  While it is `false`, `latest_ledger` is `0` and no events have been processed
  yet.
- `contract_configured` is `false` when `STREAM_CONTRACT_ID` is unset or is not
  a real `C...` contract address. In that case no stream events can be decoded
  and `/streams` stays empty.
- `latest_ledger` is the most recently observed ledger sequence number.
- `indexed_streams` is the number of streams currently held in memory.

## Response headers

| Header | When | Meaning |
|---|---|---|
| `Content-Type` | Every response | `application/json` |
| `X-Total-Count` | List endpoints: `/streams`, `/senders/:address`, `/recipients/:address` | The number of matching items **before** `limit`/`offset` are applied |

`X-Total-Count` is exposed to browsers via `Access-Control-Expose-Headers`, so
cross-origin scripts can read it and page through list results. See
[Filtering and pagination](/docs/api/streams#filtering-and-pagination) on the
Streams page for how `limit` and `offset` interact with it.

## CORS

`Access-Control-Allow-Origin` defaults to `*` (any origin). Setting
`CORS_ALLOWED_ORIGINS` to a comma-separated list of origins restricts it to
only those origins; leaving it unset, or setting it to a lone `*`, means any
origin. Whitespace and trailing slashes are trimmed from each entry, empty
entries are dropped, and any entry that is not a valid HTTP header value is
skipped with a warning rather than aborting startup.

Allowed methods are `GET`, `HEAD`, and `OPTIONS`. Only the `Accept` and
`Content-Type` request headers are allowed. `X-Total-Count` is exposed to
browsers via `Access-Control-Expose-Headers` so cross-origin scripts can page
through list results.

The policy is permissive by default because every endpoint is read-only public
data with no notion of a logged-in user -- there is nothing a cross-origin
request could do here that a same-origin one couldn't.

## Environment variables

| Name | Default | Meaning |
|---|---|---|
| `SOROBAN_RPC_URL` | `https://soroban-testnet.stellar.org` | Soroban RPC endpoint the indexer polls for events. |
| `STREAM_CONTRACT_ID` | _(placeholder -- not a real address)_ | The Stream contract id to index. When unset or left as the placeholder, the indexer runs but `/streams` stays empty. |
| `BIND_ADDR` | `0.0.0.0:8080` | Address and port the HTTP server binds to. |
| `POLL_INTERVAL_SECS` | `10` | Seconds between Soroban RPC polls. A non-integer value is ignored and the default is used. |
| `INDEXER_BACKFILL_LEDGERS` | `17280` | How many ledgers back the indexer starts from on boot. A non-integer value is ignored and the default is used. |
| `CORS_ALLOWED_ORIGINS` | _(unset -- any origin)_ | Comma-separated list of allowed origins; unset or `*` means any origin. |
| `RUST_LOG` | `info` | Log filter for the service (e.g. `debug`, `info`, `warn`). |

## Operations

### Logging

The server initialises tracing with an `EnvFilter` built from `RUST_LOG`, so
log verbosity is controlled entirely by that variable. If `RUST_LOG` is unset,
the filter falls back to `info`.

```bash
# Default level
RUST_LOG=info cargo run

# Verbose output, including indexer internals
RUST_LOG=debug cargo run

# Per-crate filters: verbose for the API crate, quieter for its dependencies
RUST_LOG=stellar_stream_hive_api=debug,tower_http=info cargo run
```

Per-crate filters use the crate/module names as they appear in the source, so
you can raise verbosity for one component without flooding the output from
everything else.

### Graceful shutdown

The server listens for `Ctrl-C` (SIGINT) and, on Unix, SIGTERM. When either
signal arrives it stops accepting new connections and shuts the HTTP server
down gracefully rather than terminating abruptly. This is what lets a process
manager or container runtime stop the service with a normal signal.

## Running the API in production

The API is a single process that reads everything from Soroban RPC and keeps
its index in memory. This checklist covers only behaviour implemented in
`api/`; it does not assume any particular hosting platform or instance size.

- [ ] **Point `SOROBAN_RPC_URL` at the RPC you intend to use.** It defaults to
      the public testnet endpoint. Every stream the API knows about comes from
      that RPC's `getEvents` responses.
- [ ] **Set `STREAM_CONTRACT_ID` to your real Stream contract `C...` address.**
      The default is a placeholder that is not a real contract address. With
      the placeholder, the process still starts and tracks ledgers, but
      `contract_configured` is `false` in [`/ready`](#get-ready) and `/streams`
      stays empty because there is no contract id to match events against.
- [ ] **Keep `INDEXER_BACKFILL_LEDGERS` inside the RPC's event retention.** On
      boot, the first poll starts that many ledgers behind the tip (the default
      is listed in [Environment variables](#environment-variables)). If that
      start ledger is older than the RPC's retention, the RPC rejects the
      range and the indexer falls back to starting at the tip, so those older
      events are not recovered. Use a window the RPC can actually serve and
      that covers the history you need.
- [ ] **Restrict `CORS_ALLOWED_ORIGINS` if browsers will call the API.** It is
      unset by default, which means any origin is allowed; a lone `*` means the
      same thing. Set it to a comma-separated list of your frontend's origins
      to narrow it -- see [CORS](#cors).
- [ ] **Check [`/ready`](#health-and-readiness) before treating the API as
      usable.** `/health` only says the HTTP server is up. `/ready` also always
      returns `200`, so read the body: wait for `synced` and
      `contract_configured` to be `true`, and check that `latest_ledger` and
      `indexed_streams` are consistent with what you expect.
- [ ] **Expect the index to be rebuilt after a restart.** There is no database:
      all state lives in memory. A restart starts with an empty index and
      re-reads recent events within the backfill window above, so streams whose
      `create` event falls outside that window will not reappear. See
      [Why `/streams/:id` can 404 even for a real stream id](#why-streamsid-can-404-even-for-a-real-stream-id).
